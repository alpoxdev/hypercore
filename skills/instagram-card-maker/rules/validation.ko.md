# 검증

> 영어 정본: [`validation.md`](validation.md)

전달 전과 이 패키지가 바뀔 때마다 읽습니다. 이 파일은 전달 전 점검표와 실패 처리를 다룹니다.

## 1. 전달 전 점검표

- [ ] 시작 질문에 답했고 전달이 고른 형식과 맞습니다. 형식을 밝혔고 사용자가 달리 요청하지 않았으면 4:5입니다.
- [ ] 브리프에 사실이 없을 때 리서치가 돌았습니다. URL·날짜가 있는 출처 사실, 카드별 독자 질문, 지어낸 경험 없음.
- [ ] 카드 수가 2~20입니다.
- [ ] 커버만 제목을 `bottom-left`에 고정하고 본문은 내용·이미지에 맞는 배치 사유가 있습니다. 사진과 글자가 분리된 레이어이고 제공된 로고가 바뀌지 않았습니다.
- [ ] 카드마다 `scene`, `visualType`, `layout`, `layoutReason`이 있고 장면·종류 변화가 서사를 뒷받침합니다. 같은 사진에는 명시적인 `reuseReason`이 있습니다. 장면 이름만 비교하지 않고 실제 이미지를 확인합니다.
- [ ] 상단·중앙·하단 배치 모두 실제 글자 영역의 대비를 유지하고 브랜드·로고와 겹치지 않습니다. 저장 HTML을 다시 열어도 배치와 이미지 계획이 같습니다.
- [ ] 사진 배경만 살짝 흐려졌습니다. 글자가 사진 위 반투명 검정 어둠막 위에 있어 사진이 글자 아래에서 보이면서 흰 글자가 대비를 유지합니다.
- [ ] `window.cardStudio.render`가 해결됐고 `#status[data-error]`가 `true`가 아닙니다.
- [ ] 고른 크기의 실제 PNG가 카드마다 한 장씩 게시 순서대로 있습니다.
- [ ] `caption.txt`가 게시 순서이고 `alt-text.json`이 카드 수·순서와 맞습니다.
- [ ] 모든 사진의 출처가 기록됐고 생성 사진은 일러스트로 표시됐습니다.
- [ ] `index.html`이 모든 이미지와 폰트 데이터를 data URI로 내장하고 원격 스크립트와 네트워크 의존성이 없습니다.
- [ ] 시스템 대체 글꼴을 쓸 때 한글 글리프를 검수했습니다.
- [ ] 다른 스킬을 지목·요구·읽지 않았고 게시·예약·업로드 경로를 쓰지 않았습니다.

## 2. 컴포저 실패 처리

컴포저는 [`../references/output-contract.ko.md`](../references/output-contract.ko.md) §4의 실패에 예외를 던지고 `#status[data-error="true"]`를 설정합니다.

- 스키마나 규격 오류면 입력 문서를 고칩니다.
- 커버·본문 배치가 잘못됐거나 사유 없이 사진이 반복되면 검증을 우회할 상투적인 이유를 넣지 않고 계획을 고칩니다.
- 누락·깨진 이미지면 `photo` 값을 고칩니다.
- 오버플로 오류면 카드를 나누거나 글자를 줄입니다. 글꼴을 축소하지 않습니다.
- `fontData` 로딩 오류면 올바른 폰트 데이터를 넣거나 `fontData`를 빼고 시스템 대체 글꼴을 씁니다.
- 렌더링 뒤 JSON을 편집하면 출력이 비워집니다. 내보내기 전에 다시 렌더링합니다.

## 3. 루프와 종료

구성 → 이 점검표와 컴포저 검증 → 강제 실패 수정. 최대 두 번입니다. 두 번을 지나면 남은 항목을 밝히고 전달합니다. 필수 사실의 근거를 찾지 못하면 필요한 출처를 밝히고 중단합니다. 게시·예약·업로드는 하지 않습니다.

## 4. 패키지 변경 점검표

이 패키지가 바뀔 때만:

- [ ] 모든 마크다운 파일의 KO/EN 짝이 유지됩니다.
- [ ] 저장소 코퍼스 검증기가 이 패키지에 대해 통과합니다. `--root skills --only instagram-card-maker --json`으로 실행합니다.
- [ ] 패키지 저작 검증기가 `--require-self-containment`와 이 패키지의 eval 파일을 `--evals`로 받아 통과하며, 이 패키지에 대한 오류를 보고하지 않습니다.
- [ ] `bun run --cwd scripts verify`가 통과합니다.
- [ ] 이번 변경이 스킬을 추가하므로 `README.md`의 스킬 수와 카탈로그 행을 갱신합니다.
