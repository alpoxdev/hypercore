## Release status

- Verbatim, from the Start overview page: "TanStack Start is currently in the **Release Candidate** stage! This means it is considered feature-complete and its API is considered stable." The same note continues "**This does not mean it is bug-free or without issues**, which is why we invite you to try it out and provide feedback".
- No v1 GA announcement exists; treat Start as pre-1.0 and its experimental surfaces (import protection, deferred hydration, static server functions, RSC) as unstable.
- Source: <https://tanstack.com/start/latest/docs/framework/react/overview.md>

## Project structure

- Start's plugin defaults `srcDirectory` to `'src'`, and the routes directory resolves to `<srcDirectory>/routes` unless overridden through `tanstackStart({ router: { routesDirectory } })` — derive the real route root from config instead of hard-coding `src/routes`.
- The docs' typical shape is `src/routes`, `src/router.tsx`, generated `src/routeTree.gen.ts`, `src/styles.css`, optional `src/types`, `public/`, a root bundler config (`vite.config.ts` or `rsbuild.config.ts`), `package.json`, and `tsconfig.json`.
- `routeTree.gen.ts` is generated by Router tooling. The Router FAQ says it should be committed — "it is essentially part of your application's runtime, not a build artifact" — and the file-based-routing API page advises ignoring the generated path from linters and formatters. Do not hand-edit it (Hypercore convention).
- File organization: the server-functions guide presents the `*.functions.ts` (server function wrappers, safe to import anywhere) / `*.server.ts` (server-only helpers) / plain `*.ts` (client-safe) split as "one approach", not a mandate.
- `.functions.ts` is **not** enforced by import protection. The import-protection guide's default file patterns are only `**/*.server.*` and `**/*.client.*`; `.functions.ts` appears solely in the file-organization section of the server-functions guide.

## Router setup

- `src/router.tsx` must export a `getRouter` function that returns a new router instance on every call. The official example uses a function declaration: `export function getRouter() { ... }`.
- Source: <https://tanstack.com/start/latest/docs/framework/react/guide/routing.md>

## Server functions

- `createServerFn()` defines a server function. `method` defaults to `'GET'`, and `Method` is exactly `'GET' | 'POST'` — no other verb exists (`packages/start-client-core/src/createServerFn.ts:449`, `:84-86`).
- `.validator(...)` is canonical. `.inputValidator(...)` is the deprecated alias and still resolves at runtime — the source marks it `/** @deprecated Use \`validator\` instead. */` and reads `const validator = options.validator ?? options.inputValidator`.
- Zod schemas pass directly to `.validator(...)`. Validator input types must be serializable; `FormData` is also allowed for `POST` server functions.
- A builder carries a **single** validator — `.validator(...)` sets it (a later call replaces the earlier one) — while `.middleware([...])` is repeatable and merges with previously supplied middleware.
- The `strict` option exists and defaults to `strict: true`. It governs TypeScript-level serialization checks; `createServerFn({ strict: false })` and the granular `strict: { input: false }` / `strict: { output: false }` forms opt out. The docs warn that `strict: false` only relaxes the type checks — the runtime serialization layer still has to handle the values.
- Server functions are same-origin app RPC endpoints, callable from loaders, components, hooks, other server functions, and event handlers; `useServerFn()` is the React wrapper when hook ergonomics are needed.
- Sources:
  - <https://tanstack.com/start/latest/docs/framework/react/guide/server-functions.md>
  - <https://raw.githubusercontent.com/TanStack/router/fe7f1fd0e6ef73c3f341dd2338b406749538a85d/packages/start-client-core/src/createServerFn.ts>

## Execution model

- Start code is isomorphic by default — it runs and is bundled in both environments unless explicitly constrained — and route loaders are isomorphic, not server-only (they run on the server during SSR and on the client during navigation).
- The execution-control primitives are `createServerFn`, `createServerOnlyFn`, `createClientOnlyFn`, and `createIsomorphicFn`.
- `createIsomorphicFn()` composes one function with per-environment implementations via `.server(...)` and `.client(...)`; a missing side is a no-op returning `undefined`, not an error. Environment functions are tree-shaken per bundle.
- `createServerOnlyFn(...)` and `createClientOnlyFn(...)` enforce environment-bound execution and throw descriptive runtime errors when called in the wrong environment.
- Secrets, DB access, filesystem access, and privileged SDK calls must sit behind server-only or server-function boundaries.
- Sources:
  - <https://tanstack.com/start/latest/docs/framework/react/guide/execution-model.md>
  - <https://tanstack.com/start/latest/docs/framework/react/guide/code-execution-patterns.md>
  - <https://tanstack.com/start/latest/docs/framework/react/guide/environment-functions.md>

## Import protection

- **Status: Experimental.** The page opens with `> **Experimental:** Import protection is experimental and subject to change.` Treat the option surface as unstable.
- Enabled out of the box. Documented defaults: `enabled: true`; `behavior: { dev: 'mock', build: 'error' }`; `log: 'once'` (deduplicates repeated violations); `include` = Start's `srcDirectory`; `exclude: []`; `maxTraceDepth: 20`.
- Default deny rules: `client.files` = `['**/*.server.*']`, `server.files` = `['**/*.client.*']`, `client.specifiers` = the framework server specifiers, `server.specifiers` = `[]`, and both `excludeFiles` = `['**/node_modules/**']`.
- **Replace vs additive is the trap.** Per the option table: `client.specifiers` is **additive with defaults**; `client.files`, `client.excludeFiles`, `server.files`, `server.specifiers`, and `server.excludeFiles` **replace** the defaults. `excludeFiles` **fully replaces** `['**/node_modules/**']` — to exclude extra paths while still skipping `node_modules`, pass both. Setting `client.files` without carrying `'**/*.server.*'` silently drops the default deny rule.
- Type-only imports and re-exports are ignored because they are erased at runtime; mixed imports still count when they carry at least one runtime value.
- Side-effect marker imports remain available for explicit boundaries: `@tanstack/react-start/server-only` and `@tanstack/react-start/client-only`.
- `mockAccess` (`'error' | 'warn' | 'off'`) exists in `packages/start-plugin-core/src/schema.ts:42` but is **absent from the import-protection guide's option table**. It is a real, undocumented schema option — label it as such and never present it as documented.
- Sources:
  - <https://tanstack.com/start/latest/docs/framework/react/guide/import-protection.md>
  - <https://raw.githubusercontent.com/TanStack/router/fe7f1fd0e6ef73c3f341dd2338b406749538a85d/packages/start-plugin-core/src/schema.ts>

## Middleware

- Two middleware types. **Request middleware** customizes any server request; **server function middleware** is a subset that adds server-function-only features such as input validation and client-side logic. Request middleware uses `createMiddleware()` (or `createMiddleware({ type: 'request' })`); server function middleware uses `createMiddleware({ type: 'function' })`.
- Middleware input validation uses `.validator(...)` too — the same rename applies, and `packages/start-client-core/src/createMiddleware.ts:182-183` carries the same `@deprecated` marker on `inputValidator`.
- `sendContext` is explicit and one-directional per hop. Client context is **not** sent to the server by default; it must be passed through `next({ sendContext: {...} })`, and anything the client can send, the client can lie about.
- **"Shape validation is not authorization."** A parsed UUID or number is a well-formed identifier, not an authorized one. When the value selects which rows get read or written — a query key, filter, or path parameter — the session principal's access to it must be verified separately, or a logged-in user can rewrite the value in their own request and reach other tenants' data.
- The docs' required pattern: "Always derive the session itself from a server-trusted source (a cookie + DB lookup in `authMiddleware`), never from `sendContext`."
- **CSRF.** `createCsrfMiddleware()` protects server functions from cross-site requests; its options are `filter`, `origin`, and `allowRequestsWithoutOriginCheck`. By default `Origin` and `Referer` are compared against the incoming request URL origin, and requests carrying none of `Sec-Fetch-Site`, `Origin`, or `Referer` are rejected.
- **The CSRF trap:** if the app does not define `src/start.ts`, Start installs its CSRF middleware automatically for server functions. Defining `src/start.ts` silently drops that automatic installation, so the file must add `requestMiddleware: [createCsrfMiddleware()]` explicitly. Start logs a development warning for server function requests when `src/start.ts` exists without it; `disableCsrfMiddlewareWarning: true` suppresses the warning for apps that handle CSRF another way.
- Sources:

## Server routes

- Server routes are declared by adding `server` to a route file's `createFileRoute(...)(...)` call and follow Router's file-based routing conventions.
- `handlers` is either an object mapping HTTP methods to handler functions, or a function that receives `createHandlers` for handlers that need their own middleware composition. An optional route-level `middleware` array applies to all handlers and runs before handler-specific middleware.
- Pathless layout routes and break-out routes are supported for grouping server-route middleware: a pathless layout adds middleware to a group of routes, and a break-out route escapes parent middleware.
- Methods beyond GET and POST (`PUT`, `PATCH`, `DELETE`) are supported on server routes.
- Source: <https://tanstack.com/start/latest/docs/framework/react/guide/server-routes.md>

## SSR, hydration, and rendering

- Routes matching the initial request render on the server by default. Per-route `ssr` defaults to `true`, and `createStart({ defaultSsr: false })` changes that default.
- Hydration mismatches come from `Intl` locale/time-zone differences, `Date.now()`, random IDs, responsive-only logic, feature flags, and user preferences. The documented fix is to compute once on the server from a cookie (preferred) or the `Accept-Language` header and hydrate that as initial state.
- **Deferred hydration is experimental**: `<Hydrate>` with strategies imported from `@tanstack/react-start/hydration`.
- ISR is available: static prerendering plus standard HTTP cache headers plus revalidation, deliberately CDN-agnostic.
- Sources:

## Platform and tooling

- Two official bundlers: Vite (the default) and **Rsbuild**, imported as `@tanstack/react-start/plugin/rsbuild` from `rsbuild.config.ts`. An Rsbuild production build emits client assets in `dist/client` and a server bundle in `dist/server/index.js`.
- `autoCodeSplitting` is a bundler-plugin option that defaults to `false` (v2 will default it to `true`). The Start plugin's config schema omits it (`configSchema.omit({ autoCodeSplitting: true, target: true })`), so it **cannot** be passed through `tanstackStart()`.
- Client-exposed environment variables use the build tool's public prefix — `VITE_` for Vite, `PUBLIC_` for Rsbuild.
- `src/server.ts` is the optional server entry point, using the fetch-style `ServerEntry` shape; when it is absent Start supplies a default.
- Static server functions are **experimental** (`staticFunctionMiddleware` from `@tanstack/start-static-server-functions`).
- Scaffolding: `npx @tanstack/cli@latest create` (`@tanstack/cli` `0.71.0`) or TanStack Builder. The legacy aliases `create-tsrouter-app`, `create-start-app`, `create-tanstack-app`, `create-tanstack`, and `@tanstack/create-start` print deprecation warnings.
