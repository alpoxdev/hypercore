# Graph Patterns

그래프로 설계한 시스템을 조립하는 반복 토폴로지, 각 패턴이 상태와 엣지에 요구하는 것, 그리고 각 패턴을 평가하는 방법.

> 영어판: [`graph-patterns.md`](graph-patterns.md)

## Reading this document

아래 모양들은 프레임워크 목록이 아니다. Anthropic은 2026년의 어휘가 생기기 전인 2024년 12월에 이 중 다섯 가지를 조합 가능한 워크플로 패턴으로 이름 붙였고, LangChain과 Google Cloud와 PuppyGraph, 그리고 Microsoft의 orchestration 문서는 서로 다른 이름으로 겹치는 집합을 설명한다. 이식 가능한 것은 각 모양이 부과하는 **계약**이다. 상태가 무엇을 실어야 하는지, join이 어떻게 결정하는지, 부주의하게 조립하면 무엇이 실패하는지다.

모든 패턴을 두 축이 정리한다.

- **경로를 누가 고정하는가** — 코드(고정 엣지), 상태(조건부 엣지), 모델(경로 값), 실행 중 발견(동적 fan-out).
- **작업이 다시 합쳐지는가** — 선형 체인은 합쳐지지 않고, fan-out은 join을 선언해야 하며, 사이클은 구조상 다시 합쳐진다.

## P1 — 순차 파이프라인(prompt chaining)

| 측면 | 계약 |
|---|---|
| 모양 | 노드 A → B → C, 각 노드가 앞 노드의 출력을 소비한다 |
| 라우팅 권한 | 코드, 모든 엣지 고정 |
| 상태 | 단계별 인계 산출물. 공유 가변 필드 없음 |
| join | 없음 |
| 실패 | 단계 사이에 게이트가 없으면 잘못된 중간 산출물이 조용히 전파된다 |
| 평가 | 산출물에 대한 단계별 단정과 최종 출력 |

Anthropic의 조건은 작업이 "고정된 하위 작업으로 쉽고 깔끔하게 분해"될 수 있고, 중간 단계에 프로그램적 검사를 둘 수 있다는 것이다. 이 패턴은 각 호출을 더 쉬운 일로 만들어 지연을 정확도와 맞바꾼다. Google Cloud가 같은 조언을 하는 방식은 엣지 목록을 왼쪽에서 오른쪽으로 읽는 것이다.

분해가 입력 도착 전에 정해져 있고 각 단계를 따로 시험할 수 있을 때 쓴다. 뒤 단계가 작업을 되돌려 보내야 할 수 있다면 쓰지 않는다. 그때는 P5다.

## P2 — 라우팅

| 측면 | 계약 |
|---|---|
| 모양 | 분류 → N개 전문 분기 중 하나 |
| 라우팅 권한 | 코드(결정적) 또는 모델(agent router) |
| 상태 | 분류 결과와, 각 분기가 기대하는 payload |
| join | 없음. 분기는 각자 종료한다 |
| 실패 | 테스트가 한 분기만 건드려 두 분기의 품질이 벌어진다 |
| 평가 | 분류 정확도와 분기 품질을 따로 |

Google Cloud의 표가 이 선택을 가장 깔끔하게 정리한다. 결정적 라우터는 "코드의 규칙"을 쓰고 모델 호출이 필요 없으며, agent router는 입력을 해석하므로 모델 호출이 한 번 필요하다. 잘 작동하는 조합은 정적 그래프 안의 agent router다. "모델의 선택은 달라지지만, 가능한 연결은 그대로"이기 때문이다.

분기는 프롬프트나 도구 집합이나 eval이 형제와 다를 때만 새로 만든다. 모든 것을 형제와 공유하는 분기는 라우트가 아니라 조건문이다.

## P3 — 병렬 fan-out과 gather

| 측면 | 계약 |
|---|---|
| 모양 | 독립 분기로 나눈 뒤 join |
| 라우팅 권한 | 분할은 코드, join 조건도 코드 |
| 상태 | 분기마다 필드 하나, 또는 분기가 같은 필드에 덧붙인다면 선언된 reducer |
| join | 선언된 형태. ADK의 `JoinNode`는 노드 이름을 키로 하는 사전을, `parallel_worker`는 입력 순서를 지킨 목록을 돌려준다 |
| 실패 | 출력 없이 끝난 분기는 join에 그 분기의 값을 남기지 않고, 오류는 하류에서 드러난다 |
| 평가 | 분기별 정확성, join 완전성, 전체 합의 |

Anthropic이 eval이 달라서 나눠 두는 두 변형이 있다.

- **sectioning** — 서로 다른 하위 작업을 병렬로(정확성 점검, 보안 점검, 문서 점검).
- **voting** — 같은 작업을 여러 번 실행한다. 실행 전에 집계 규칙(다수결, 임계값, 하나라도 걸리면)을 선언해야 한다.

루트 계약의 한도를 적용한다. fan-out은 노드별로, 실행별로 상한을 둔다(GE-F-2). Anthropic의 초기 조사 시스템은 단순한 질의에 subagent 50개를 만들었고, 현재 공개된 지침은 복잡도에 맞춰 노력을 배분한다.

## P4 — Orchestrator-worker

| 측면 | 계약 |
|---|---|
| 모양 | 리드 노드가 실행 중에 분해하고 위임한 뒤 종합한다 |
| 라우팅 권한 | 분해는 모델, 위임 봉투는 코드 |
| 상태 | 작업자별 결과 자리와 종합 입력. 작업자 수는 실행 전에 알 수 없다 |
| join | 종합 노드. 누락되거나 실패한 작업자를 명시적으로 감당해야 한다 |
| 실패 | 중복 작업, 빈틈, 무제한 지출 |
| 평가 | 분해된 하위 작업의 포괄성과 실행당 비용 |

P3와의 차이는 하위 작업이 미리 정해져 있지 않다는 점이다. 입력을 보고 orchestrator가 정한다. Anthropic은 이 방식을 성립시키는 위임 계약을 설명한다. subagent마다 목표, 출력 형식, 사용할 도구와 출처에 대한 안내, 분명한 작업 경계가 필요하며, 모호한 지시는 중복 검색을 낳았다고 보고한다.

PuppyGraph의 경고가 여기에 가장 잘 적용된다. 어떤 작업을 별도 노드로 만들지 정하는 결정에는 값이 붙고, 기회가 될 때마다 노드를 늘리는 시스템은 그 값을 치르면서 이득은 안정적으로 얻지 못한다.

## P5 — Evaluator-optimizer(사이클)

| 측면 | 계약 |
|---|---|
| 모양 | 생산자 → 검증자 → 판정이 실패하는 동안 생산자로 돌아가는 back-edge |
| 라우팅 권한 | 검증자의 구조화된 판정을 읽는 코드 |
| 상태 | 현재 산출물, 판정, 시도 횟수 |
| join | back-edge가 join이다. 최대 통과 횟수를 선언해야 한다(GE-4) |
| 실패 | 아무도 선언하지 않은 임계값에서 멈추거나, 검증자가 생산자라서 영원히 멈추지 않는다 |
| 평가 | 시도 횟수별 통과율과 추가 반복의 한계 이득 |

루트 계약의 두 규칙이 여기에 걸린다. 검증자는 생산자와 다른 노드이고(GE-V-1), 사이클은 노드 자체의 조건만이 아니라 그래프 수준에서 한정된다.

이 패턴은 루프 계약과 그래프 계약이 만나는 자리다. 루프는 *이번* 시도가 끝났는지 정하고, 그래프는 시도가 몇 번 존재하는지 정한다. 종료 조건 규칙 자체는 [`instructions/loop-engineering/LOOP_ENGINEERING.ko.md`](../../loop-engineering/LOOP_ENGINEERING.ko.md)에 속한다.

## P6 — Supervisor와 handoff 트리

| 측면 | 계약 |
|---|---|
| 모양 | 분류 노드가 전문가에게 통제를 넘기거나, 전문가를 호출하고 통제를 유지한다 |
| 라우팅 권한 | 모델. 단, 목적지 집합은 그래프에 고정된다 |
| 상태 | 대화나 작업의 소유권이 이동하므로 명시적이어야 한다 |
| join | 없음. 통제는 암묵적으로 돌아오지 않는다 |
| 실패 | 통제를 돌려주지 않는 전문가, 또는 모든 하위 작업을 병목으로 만드는 관리자 |
| 평가 | 라우팅 정확도와 handoff 이후의 턴 소유권 |

구분은 OpenAI SDK가 문서화한 그대로다. agents as tools에서는 관리자가 대화를 쥐고 제한된 하위 작업만 전문가에게 맡기고, handoff에서는 전문가가 그 턴의 남은 부분에 대해 활성 에이전트가 된다. 같은 화살표가 둘 다를 가리키므로, 그래프는 각 엣지가 어느 쪽인지 기록해야 한다.

## P7 — 동적 map-reduce

| 측면 | 계약 |
|---|---|
| 모양 | 노드가 실행 중에 하류 노드를 몇 개 만들지 정한다 |
| 라우팅 권한 | 코드. 모델이 만든 계획이나 데이터에서 나온 개수를 따른다 |
| 상태 | 분기별 상태는 격리되거나 선언된 reducer로 병합된다. LangGraph의 `Send`는 각 전송에 별도 상태를 넘긴다 |
| join | 수집 노드. 분기 개수는 trace의 일부다 |
| 실패 | 분기 개수가 기록되지 않아 실패를 재현할 수 없다(GE-E-3) |
| 평가 | 항목별 정확성과 수집의 정렬·중복 제거 규칙 |

LangGraph는 이것을 map-reduce로 문서화한다. 엣지가 미리 정해지지 않았고, 노드가 하나 이상의 하류 노드로 작업을 동적으로 보낸다. Google Cloud의 `parallel_worker`는 목록 입력에 대한 같은 모양이며, 결과를 입력 순서로 모은다.

## P8 — 중첩 그래프(워크플로를 노드로)

| 측면 | 계약 |
|---|---|
| 모양 | 그래프 전체가 상위 그래프의 노드 하나가 된다 |
| 라우팅 권한 | 상속된다. 자식은 자기 진입점과 종료점만 노출한다 |
| 상태 | 부모와 자식 사이의 선언된 입출력 경계. 공유 가변 상태가 아니다 |
| join | 자식의 종료 노드 |
| 실패 | 경계가 강제되지 않아 부모가 자식 내부를 들여다본다 |
| 평가 | 자식 계약 시험과 상위 수준 동작 |

Microsoft는 sub-workflow를 더 큰 그래프 안의 executor로 문서화하고, ADK는 "`Workflow`도 노드"라고 밝히며, PuppyGraph는 계층형·중첩 그래프를 원래 패턴 집합이 아니라 프레임워크에서 나온 모양으로 분류한다.

중첩은 큰 시스템을 검토 가능하게 유지하는 방법이자, 그래프를 시험 불가능하게 만드는 방법이다. 자식의 경계가 실제 계약이 아니면 부모의 테스트가 그 안까지 들어간다.

## Choosing a shape

| 질문 | 답 | 모양 |
|---|---|---|
| 분해가 입력 도착 전에 정해지는가 | 예, 순서가 있다 | P1 |
| 서로 구별되는 입력 범주가 작은 집합인가 | 예 | P2 |
| 하위 작업이 독립적이고 미리 알려져 있는가 | 예 | P3 |
| 하위 작업이 실행 중 발견에 따라 달라지는가 | 예 | P4 |
| 한 번 더 시도하면 품질이 오르는가 | 예, 기준을 표현할 수 있다 | P5 |
| 전문가가 그 턴의 나머지를 소유해야 하는가 | 예 | P6 |
| 분기 개수가 데이터에 달려 있는가 | 예 | P7 |
| 토폴로지가 한 화면에서 검토하기에 너무 큰가 | 예 | P8 |

실제 시스템 대부분은 조합이다. 앞단의 P2 라우터, 분기 안의 P3, 산출물을 지키는 P5, 각 단계를 감싸는 P8. 조합 규칙은 기본 규칙과 같다. 노드 하나에 라우팅 방식 하나(GE-E-2)를 모든 수준에서 적용한다.
