# 루프 유형

> 영어판: [`loop-types.md`](loop-types.md)

모든 루프는 두 축 위의 선택이다. 무엇이 이터레이션을 시작하는가, 무엇이 루프를 끝내는가. 벤더의 분류는 그 축 위의 지점에 이름을 붙인 것이지 축을 대신하지 않는다. 이 문서는 유형을 의식적으로 고르는 데 쓴다. 제품 기능을 고르는 데 쓰지 않는다.

근거: 네 가지 유형 분류와 그 정렬 기준은 Claude Code 팀의 것이다(2026-11-03 확인). 역할 기반 분류(실행, 과업, 제품, 시스템, 감독)는 Laurie Voss의 것이다(2026-11-03 확인). 루프를 겹치는 관점은 swyx의 것이고, LangChain이 프리미티브와 함께 다시 정리했다(둘 다 2026-11-03 확인). 문서화된 동작이 아니라 실무자의 의견인 주장에는 **의견** 표시를 붙였다.

## 축 1 — 트리거

| 트리거 분류 | 발동 시점 | 첫 행동까지 지연 | 무너지는 지점 |
|---|---|---|---|
| 사람 턴 | 사람이 프롬프트를 보낼 때 | 초 | 준수 여부가 설계가 아니라 사람에게 달린다 |
| 조건, 사람이 시작 | 사람이 조건을 한 번 진술하고, 턴마다 다시 검사한다 | 초에서 분 | 조건이 모호해서 검사자가 실패시킬 수 없다 |
| 시간 간격 | 타이머가 도달할 때 | 간격만큼 | 간격이 변화 속도보다 짧다 |
| 이벤트 | 저장소 이벤트, 웹훅, 큐 항목이 도착할 때 | 초 | 이벤트 원천을 신뢰할 수 없거나, 한꺼번에 몰려온다 |
| 연쇄 | 사람 입력 없이 직전 턴이 끝날 때 | 즉시 | 진전 신호가 없으면 공회전이 된다 |

## 축 2 — 정지

| 정지 분류 | 검사 주체 | 신뢰 수준 | 비용 양상 |
|---|---|---|---|
| 모델 판단 | 작업 중인 에이전트 | 가장 낮음. 자기 채점이다 | 예측 불가. 일찍 끝나거나 늦게 끝난다 |
| 조건 + 독립 검사자 | 대화 기록만 보는 별도 모델 | 중간 | 턴당 평가 비용. 보통 본 턴에 비해 작다 |
| 조건 + 도구를 쓰는 검사자 | 명령을 실행하거나 파일을 읽는 검증기 | 더 높고, 비용도 더 높다 | 이터레이션마다 검증 작업이 붙는다 |
| 결정적 오라클 | 테스트, 종료 코드, 스키마 검증, 개수 | 가장 높음 | 이터레이션당 가장 싸다 |
| 작업 큐 비어 있음 | 큐 | 큐가 권위 있다면 높음 | 입력 크기로 상한이 정해진다 |
| 예산 소진 | 카운터 | 확실 | 성공이 아니라 정지다 |
| 사람의 취소 | 운영자 | 확실 | 일시정지 경로가 동작해야 성립한다 |

`신뢰 수준` 열을 신뢰 순으로 읽는 것이 요점이다. 독립된 모델은 자기 판단보다 낫고, 결정적 오라클은 둘보다 낫다. Claude Code 팀도 반대 방향에서 같은 선호를 밝힌다. 목표 기반 루프에서 결정적 기준이 "매우 효과적"인 이유는 에이전트가 "충분히 좋음"을 더 이상 판단하지 않아도 되기 때문이다(2026-11-03 확인).

## 이름이 붙은 네 가지 유형

| 유형 | 트리거 | 벤더가 서술한 정지 기준 | 맞는 작업 | 벤더가 권하는 사용량 관리 |
|---|---|---|---|---|
| 턴 기반 | 사용자 프롬프트 | "Claude가 작업을 마쳤거나 추가 컨텍스트가 필요하다고 판단" | 정기 절차나 일정에 속하지 않는 짧은 작업 | 구체적 프롬프트와 스킬로 검증을 인코딩해 턴 수를 줄인다 |
| 목표 기반(`/goal`) | 수동 프롬프트 | "목표 달성 또는 최대 턴 수 도달" | 검증 가능한 종료 기준이 있는 작업 | 구체적인 완료 기준과 명시적 턴 상한 |
| 시간 기반(`/loop`, `/schedule`) | 지정한 시간 간격 | "사용자가 취소하거나 작업이 완료(PR 병합, 큐 소진)" | 반복 작업, 외부 시스템과의 접점 | 간격을 늘리거나, 시간 대신 이벤트에 반응한다 |
| 사전 대응(proactive) | 이벤트나 일정. 실시간 사람 없음 | 작업마다 목표 달성 시 종료. "루틴 자체는 끌 때까지 돈다" | 정의가 잘 된 작업의 반복 흐름 | 루틴은 작은 모델로 라우팅하고, 판단이 필요한 곳에 성능 높은 모델을 쓴다 |

놓치기 쉬운 성질이 두 가지다. 시간 기반 유형은 **자체 완료 의미가 없다.** 작업 완료와 루프 정지는 별개 사건이라, 이미 빈 큐를 확인하는 간격 루프는 누군가 취소할 때까지 계속 확인한다. 사전 대응 유형은 반대 모양이다. 항목마다 자기 목표에서 끝나고, 루틴에는 종료 상태가 아예 없다. 잘못 고르면 루프가 멈춰 있거나 끝나지 않는다.

## 네 이름이 다루지 않는 유형

| 유형 | 모양 | 출처 | 맞는 상황 |
|---|---|---|---|
| 과업 루프("Ralph") | 바깥 껍데기가 같은 명세로 에이전트를 다시 돌린다. 이터레이션당 작업 항목 하나, 백로그가 빌 때까지 | Geoffrey Huntley, 2025-07-14(2026-11-03 확인) | 각 단위가 독립적이고 명세가 계약인 신규 작업이나 잘 정의된 작업 |
| 검증 루프 | 안쪽 루프의 채점자가 거부하고 피드백을 돌려준다 | LangChain의 2단계(2026-11-03 확인) | 지연보다 산출물 정확성이 중요한 모든 경우 |
| 이벤트 기반 루프 | 외부 이벤트가 실행을 시작한다 | LangChain의 3단계 | 프로젝트 밖에서 작업이 들어올 때 |
| 언덕 오르기 루프 | 분석 단계가 운영 트레이스로 하네스(프롬프트, 도구, 채점자)를 고쳐 쓴다 | LangChain의 4단계 | 배울 만큼 실행 기록이 쌓인 뒤 |
| 최적화 루프 | 이터레이션마다 반증 가능한 가설 하나, 지표, 가드, 로그, 롤백 | [`../../autoresearch/AUTORESEARCH.ko.md`](../../autoresearch/AUTORESEARCH.ko.md) | 충실한 지표로 측정 가능한 개선 |
| 감독 루프 | 목표를 정하고 예산을 배분하고 작업을 쳐낸다. 사람이 소유한다 | Voss(2026-11-03 확인) | 루프가 둘 이상일 때. 어느 루프가 살아남을지 정할 주체가 필요하다 |

과업 루프에는 출처와 함께 경고를 붙인다. 저자는 이 기법을 "비결정적인 세상에서 결정적으로 나쁜" 것으로 서술하고, 이터레이션당 작업 항목 하나를 요구하며, "도구 호출과 사용량에 상한을 두지 않는" 도구가 필요하다고 적는다(2026-11-03 확인). 이터레이션당 비용 상한 없이 최종 일관성에 거는 의도적 베팅이다. 백로그가 상한이고 지출이 루프 밖에서 계량된다면 받아들일 만하다. 운영 중인 저장소의 유지보수 기본값으로는 받아들일 수 없다.

## 루프 겹치기

루프는 중첩되고, 바깥 루프가 비용과 지연을 지배한다.

| 계층 | 주기 | 무엇을 반복하는가 | 실패 신호 |
|---|---|---|---|
| 턴 | 초 | 응답 하나 안의 도구 호출 | 일찍 멈추고 성공했다고 보고한다 |
| 목표 루프 | 분에서 시간 | 조건이 성립할 때까지의 턴 | 조건이 영원히 성립하지 않거나, 약해진 검사로 성립한다 |
| 이벤트 루프 | 분에서 일 | 외부에서 도착하는 작업 항목 | 몰림과 중복 작업 |
| 메타 루프 | 일 | 루프 자체의 설정 | 측정 없는 개선 주장 |

겹친 관점이 말하는 바는 "루프를 추가한다"가 국소 변경일 수 없다는 것이다. 턴 계층의 결함은 위의 모든 계층이 증폭한다. swyx의 표현은 "루프를 최대한 효과적으로 겹치는 것이 게임"이라는 것이고, 문제가 생기면 신뢰성을 위해 루프를 내려가고, 모델이 좋아지면 레버리지를 위해 올라가라고 한다(2026-11-03 확인, **의견**). LangChain의 정리는 실무적 시험을 덧붙인다. 검증은 "실행마다 지연과 비용을 늘리므로", 틀린 결과가 비쌀 때 넣는다(2026-11-03 확인).

## 유형 고르기

| 작업 모양 | 시작점 | 올라갈 곳 |
|---|---|---|
| 일회성 변경, 범위 불명 | 턴 기반 | 없음. 루프를 만들지 않는다 |
| 검사를 쓸 수 있는 반복 작업 | 턴 상한이 있는 목표 기반 | 트리거가 신뢰할 만해지면 예약 실행 |
| 규칙은 그대로고 입력만 바뀌는 반복 작업 | 시간 기반 | 원천이 알려줄 수 있으면 이벤트 기반 |
| 정의가 잘 된 항목의 흐름(트리아지, 리뷰, 업그레이드) | 항목별 목표가 있는 사전 대응 | 겹친 구성, 그 위에 감독 루프 |
| 싸게 측정 가능한 지표 | 최적화 루프 | 트레이스가 쌓이면 언덕 오르기 |
| 정확성이 중요한 산출물 | 위 유형 안의 검증 루프 | 에이전트형 채점자 대신 결정적 오라클 |

표에서 한 줄씩만 올라간다. 첫 줄 위의 모든 유형은 운영에서만 드러나는 실패 모드를 더한다. 벤더의 권고도 "가장 단순한 해법에서 시작하고 이 패턴들을 선별적으로 쓰라"는 것이다(2026-11-03 확인).

## 유형별 실패 모드

| 유형 | 특징적 실패 | 고치는 방법 |
|---|---|---|
| 턴 기반 | 일찍 끝내고 부분 작업을 완료로 보고 | 검사를 스킬로 인코딩하고, 출력에 증거를 요구한다 |
| 목표 기반 | 조건이 느슨해 검사자가 항상 통과시킨다 | 종료 상태, 검사, 제약, 상한을 모두 적는다 |
| 시간 기반 | 작업이 끝난 뒤에도 계속 발동. 간격이 변화 속도보다 짧다 | 간격을 변화 속도에 맞추고, 큐 소진으로 끝낸다 |
| 사전 대응 | 리뷰 백로그가 사람이 읽는 속도보다 빨리 늘어난다 | 주기당 열린 항목 수를 제한하고, 사람 큐에 WIP 상한을 둔다 |
| 과업 루프 | 품질 개선 없이 이터레이션 수만 늘고, 자리표시 구현이 남는다 | 이터레이션당 항목 하나, 테스트로 배압, 루프 밖 지출 상한 |
| 검증 루프 | 채점자가 실제 검사 없이 승인한다 | 채점자에게 결정적 오라클이나 도구를 준다 |
| 최적화 루프 | 지표는 좋아지고 제품은 나빠진다 | 첫 이터레이션 전에 가드 지표를 선언한다 |
| 감독 루프 | 예산의 주인이 실제로 없다 | 루프 목록마다 소유자 한 명을 지정한다 |
